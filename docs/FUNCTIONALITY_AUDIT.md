## Actual architecture

- Backend: JavaScript ES modules, Express 5, Mongoose 9/MongoDB, Zod validation, bcrypt passwords, signed JWTs and Socket.IO 4. Modular monolith; thin controllers delegate to domain services. MongoDB transactions require a replica set.
- Frontend: React Native 0.88, Expo 58, React 19, TypeScript, React Navigation, native MapLibre and browser MapLibre GL. Existing RideCore tokens, Inter fonts and sheets should be retained.
- Persistence: User, DriverProfile, Vehicle, Ride, Payment, Rating, PhoneOtp and RideShare. Model initialization creates indexes; no versioned migration framework was found. Future schema changes need explicit compatibility/backfill notes, not an unrelated migration dependency.
- Geographic services: OpenStreetMap tiles, Nominatim text/reverse geocoding and OSRM route geometry/distance/duration. Text search is limited to `countrycodes=gm`. Coordinates are `[longitude, latitude]` throughout GeoJSON/API calls.
- Testing: Vitest/Supertest plus disposable MongoDB replica sets on the backend; Jest/React Native Testing Library on the frontend; Node integration scripts use transpiled real frontend adapters against a disposable backend.
- Runtime configuration: backend private `.env` and frontend public Expo configuration. Do not print private settings, reset the configured database or replace working server configuration.

## Visible elements and misleading states

- Payment method on Choose your ride is plain text, not a selector. Confirmation explicitly says preference is chosen after the trip.
- A no-drivers message can mean initial loading or a failed nearby API request, rather than a successful empty result.
- All category cards have server fares, but cards do not communicate current per-category supply.
- Search results can outlive their query text; they are real records, but the association with current input can be misleading.
- Services category cards navigate, but do not use the same destination-first entry path as the homepage.
- Admin dashboard controls do not exist; there is no evidence of a merely decorative admin dashboard in this checkout.
- Share My Ride controls already call real protected APIs. Demo advancement buttons are intentionally labeled and isolated; they should not be mistaken for real rider powers.

## Driver dependency chain

`register(accountType=driver)` → auto-created pending DriverProfile → licence submission → vehicle submission → human admin approves profile AND vehicle → driver sets valid `[lng,lat]` location → online → eligible nearby response → compatible requested ride within configured radius → atomic acceptance → busy → assigned-trip transitions → completion/cancellation → offline.

Phone verification is optional mock OTP and is not licence/vehicle approval. Re-entering profile/vehicle details can reset approval. Approving a driver does not make the driver online automatically. Suspension/account deactivation and active-ride constraints must remain enforced.

Current real test-account approval/location status is **unknown**. Do not assume that a seed script's log or prior session means a driver is currently eligible. Use an isolated database to demonstrate the chain and test negative cases (one approval missing, offline, busy, outside radius, mismatched category, inactive account and stale position).

## Recommended development order and review gates

These are dependency notes, not implementation prompts for later phases.

1. **Phase 1: audit, requirements traceability and reproducible evidence.** Record baseline results and missing device evidence. Repair verification tooling only in a separately authorized follow-up. Gate: reviewed audit, proposal deviations and scenario matrix.
2. **Phase 2: driver eligibility and discovery reliability.** Reproduce full isolated driver chain, handle suspended contract, distinguish loading/error/empty and establish location freshness and demo isolation. Gate: eligible driver appears, receives request and accepts; negative eligibility cases pass.
3. **Phase 3: minimal functional admin workflow.** First admin sign-in/routing and driver + vehicle review, then account/trip/payment lists and accurate aggregate counts/search. Gate: human approves a test applicant; rider/driver cannot call admin actions; driver remains offline until intentionally online.
4. **Phase 4: consistent destination-first booking and payment preference.** Home and Services use same flow; query/result consistency, manual fallback, category explanations, preserved server fare and no early payment. Gate: first-time rider can request via GPS/text/pin paths; no duplicate ride.
5. **Phase 5: map reliability/freshness across actual devices.** Build on verified supply state; test centre pin, camera, sheet/keyboard, car removal, network loss and secure-context GPS. Gate: phone evidence, not just mocked map tests.
6. **Phase 6: complete lifecycle proof and unmatched-request handling.** Reuse legal server states, restore active ride, exercise driver/rider permissions, disconnects, cancellation and ratings. Gate: persisted end-to-end journey plus controlled failures.
7. **Phase 7: verify and close sharing gaps.** Reuse existing secure feature; public recipient reachability, copy/share/revoke, expiry/end, timestamps, privacy and recovery. Gate: separate unauthenticated recipient loses access promptly after end/revoke/expiry.
8. **Phase 8: saved places and recent-history edge cases.** Minimal owner-scoped Home/Work CRUD; preserve real history/popular distinction. Gate: isolation, edit/delete/coordinate restoration tests.
9. **Phase 9: consolidated full-stack/device regression evidence.** Maintain tests each earlier phase; this gate consolidates rather than postpones testing. Test iOS/Android where practical and label unavailable checks.
10. **Phase 10: final academic report and reviewed delivery.** Resolve payment/SOS/surge scope decisions and document architecture deviations. No automatic deploy/push or claim of real transfers/alerts.

Admin UI and driver reliability are interdependent: Phase 2 can use existing protected APIs in an isolated harness to prove backend eligibility; Phase 3 supplies the human-operated path. This avoids waiting for a full analytics dashboard to test matching.
